# RouterStack Work Tracker — 产品需求与业务规则

> Status: handoff baseline, 2026-11-07. 这份文件总结用户在当前对话里最终确认的需求。它不是 RouterStack 官方计费政策。修改业务规则前，应先核实实际条款。

## 0. 核心使命

RouterStack 的 App/Invoice 记录有时遗漏工作、after-hours bonus、额外费用或结算款项；用户需要独立保存工作事实，核算应收金额，集中结款时和协调人 Tim 核对遗漏。

三个核心目标，按优先级排序：

1. **最少录入**：现场每做完一项工作，尽量少输入字段，不手动往 Excel 插入行或维护公式。
2. **独立估算与异常识别**：根据已配置费率、工时、Lunch 和 AH 规则计算理论收入，再与 RouterStack App 显示金额比较。
3. **跨结算周期追踪**：只有明确核实的未结清 Invoice 余额才结转到新周期；不得因为 App 差异或银行汇款总额推断具体哪张未付。

质量优先级：原始数据完整性 > 计算正确性及可解释性 > Excel 兼容性 > 录入便利性 > 视觉效果。

## 1. 三层架构（逻辑分离、数据统一）

```text
Tool —— 录入、编辑、异常提醒、月度视图、Tim 对账清单、周期结转
  ↕ 严格按 schema 读写
Work Log —— 保存的唯一工作/Invoice 原始事实来源（每个 Job 一张 Invoice）
  ↕ 引用规则 + 规则版本
Config —— 基础费率规则、Lunch、AH、最低计费、差额阈值与 schema 版本
```

**概念方案**：三层可放在同一个 Excel 的不同 Sheet，不一定需要数据库或独立软件。

**当前实现**：用户明确希望 Tool 是真正的可录入**小程序**，而不是只有说明文字的 Excel Sheet。因此 v0.2.0 的操作 Tool 是离线 HTML/JS，记录落在 XLSX 的 `Work Log`、规则落在 `Config`；XLSX 中另有名为 `Tool` 的只读指导/汇总 Sheet。不要把两者混为一谈。未来可以演进，但必须保持稳定、单一的数据契约。

不允许出现两份互相竞争的真实工作记录，也不应以“工具升级”为理由覆盖历史事实。

## 2. 已确认的业务语义

- 每次单独工作对应一个 Invoice ID，格式 `INV-XXXX`（现有程序支持 `INV-` 后至少四位数字）。
- **一天可能有两个甚至多个工作/地点/Invoice**；按工作分别记，不能按日期合并。
- Invoice ID 可以在录入时暂缺，日后补全；已有 ID 不得在同一个周期里重复。
- Invoice 并非日常会被作废；不需要繁琐的 Void/Reissue 流程、逐笔 Paid/Unpaid 勾选。
- RouterStack 可能隔很久一次性付款；用户最初通常只能看到**银行实际收到的总金额**，无法获得完整的逐笔清单。产生疑问后，Tim 可能发送截图，或根据用户自己的工作记录查缺补漏。
- 已确认未付的金额可以顺延到下次；**部分结算**应允许仅结转仍欠的余额，而非整笔原估算。
- 由用户确认每个具体 Invoice 的结转金额；**不能**从总额差额自动分摊到 Invoice。
- 一个 Job 的估算、App 显示、银行到账、确认结转余额是四种不同量，不能混用或互相覆盖。
- 只保存必要的工作记录与结算证据；不需要完整薪资核算或会计系统。

## 3. 字段 / UI

### 最小工作输入（快速新增）

必要：`Date`、`Start Time`、`End Time`、`Rate`。

可以留空后补：`Invoice ID`、`App Displayed`、`Note`、`Extra Cost`。

`Lunch (h)`：**数字，单位小时**，默认留空，新的记录中空白按 0 h；不得改回 Checkbox 或 Checkbox + 下拉的重复操作。历史记录如不确定是否休息，不得假定其真实休息是 0，只能在迁移时标记待确认。

工具中必须能新增、编辑、删除、查询记录；用户正常操作不应需要在 Excel 末尾手动加行。

### 主表展示精简

- 常见显示：Date、Invoice ID、Shift/Time、Lunch、Rate、`Billable (AH)`、Estimated、App Displayed、Difference、Note。
- `Billable (AH)` 合并为一列，格式如 **`8.75 (1.75)`**，括号中是 AH Paid Hours。原始小时、AH 小时仍需作为**数值**保留以支持公式、排序与测试；显示文本不能代替计算数据。
- 允许隐藏辅助列，不应因为界面简洁而丢弃原始 Start/End、Lunch、Extra 等。
- 空白的 App Displayed = **待填**，不能当 0 收入，也不应生成等于整个 Estimated 的假差额；明确录入 `0` 才视为 App 显示 0。

## 4. 金额概念（必须强制分开）

- `Estimated Net Revenue`：原 Excel 中基于工时/费率/AH 的**理论估算**；名称沿用历史，不代表已核实的税后净收入或实收。
- `Extra Cost`：附加应收费用，独立录入，有来源才计入。
- `Expected Total`：Estimated + Extra Cost（工具汇总或对账时使用）。
- `Displayed Revenue` / `App Displayed`：RouterStack App 当时展示的金额，可能漏加成或额外支出；是人工录入的原始事实，**不等于**实际银行收款。
- `Difference`：`Expected Total - App Displayed`。正数表示理论金额高于 App 金额，负数反之；是**需要解释的计算差异**，不是已证实的欠款。
- `Bank Received`：实际一次性到账总额，只能用于周期整体核对；除非拿到可证实明细，否则不能自动对应到具体 Invoice。
- `Confirmed Outstanding` / `Carryover Balance`：经核实的特定 Invoice 未结清金额，可进入下一周期；可能与 Difference 不一致。

默认应有异常提示、差额筛选、给 Tim 复制的简洁对账清单；不要强行写入 Paid/Unpaid 状态。

## 5. 当前暂用计费假设（未被 RouterStack 正式确认）

当前 V2 代码及模板使用：

- Minimum billable duration: **2 小时**。
- AH Start: **18:00**。
- AH Multiplier: **1.5×**。
- Lunch：按输入数字小时扣减，**先扣普通时段，再扣 AH 时段**（暂用假设）。
- Rate：每工作可不同，不能统一假定为某个固定时薪。
- 区分 AH Paid Hours 与整体 Billable Hours；跨午夜、最低 2 小时与 AH 叠加、扣休息位置等都需要与实际计费协议核对。

**禁止**把上述假设包装成确定的公司政策。更改 Config 时不得静默重算已经完成核对/归档的历史金额。规则及 schema 应有版本标记，历史记录必须能够解释当时的计算依据。

## 6. 结算/结转流程

1. 日常在 Tool 逐项新增记录，显式保存 Excel；工作事实始终以最新已保存 XLSX 为准。
2. App 显示金额出来后补录，查看估算差额并整理给 Tim 的清单。
3. 集中结算时记录银行实际到账的总额；如果对不上，再请求 Tim 逐笔截图或提交工作清单。
4. 按证据确认哪些 Invoice 确实未结清以及金额。不能从合计推断单项。
5. 结清后新建一个**新的周期文件**。只把用户明确勾选并输入金额的未结 Invoice 结转，允许只结转部分余额。若全部结清则新建空白文件。
6. 旧周期 Excel 完整归档；不自动迁入历史工作；新文件应包含确认的结转记录及以后新工作。
7. 新周期中的 Carryover 是**旧 Invoice 的余额引用**，不是新的工作或新 Invoice；不能计入新完成工作数量，也不能误当本周期新赚金额。

周期 = 一次实际结款/核对过程决定的文件范围，不必与自然月一致；月度统计应可从每个周期中按日期切片，不可用固定行 SUM 或假设“每个文件恰好一个月”。

## 7. 非功能需求和边界

- 离线优先；本地浏览器完成计算与 Excel 导入导出；无需账号、服务端、数据库、宏或强制联网。
- 当前保存不是自动同步：浏览器内存修改直到明确保存/下载才持久化；必须避免误导用户为“已保存”。
- 不能同时在 Excel 和 Tool 各自编辑同一文件而未经同步，否则会有覆盖冲突。
- 仓库推荐 Private；不要把真实发票、工资、银行到账、截图、个人工作簿提交到 Git。示例与测试数据必须是合成的。
- 操作语言以中文为主；变量、字段、代码术语可用英文；面向新西兰同事的对账内容宜简洁、专业、明确。
- 优先复用现有 HTML/JS/JSZip；不为赶时髦而换框架、引入云同步。

## 8. 尚未实现或仅部分实现的需求

注意不要将此前的“建议功能”全部当成现有功能：

- 真正的按月份细分 Dashboard：**未确认已实现**，现有工具主要是当前周期总览；需要以源码为准。
- 完整的“集中结算总额 vs 银行到账”的持久化对账台账：当前 V2 主要实现了 Invoice 层面**手动确认后结转**；全面的结算证据/待核对状态仍可优化。
- 规则版本化与 schema 迁移：模板有版本标记，但无通用迁移框架；要按版本和数据契约处理。
- GitHub 上实际建库、推送、Pages 部署：只交付了 starter ZIP，**不应假定远程仓库已创建**。
- 自动保存、云同步、银行流水接入、RouterStack App 接口、OCR 截图解析：**没有实现，也不是当前硬性目标**。
